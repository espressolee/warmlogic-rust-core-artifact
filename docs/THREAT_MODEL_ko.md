# WarmLogic 위협 모델

> **버전**: 1.0 (2026년 2월)
> **상태**: 감사 전 기준선
> **목적**: 제3자 보안 감사 준비를 위해 공격 표면, 위협 행위자 및 현재 완화 조치를 문서화합니다.
> 원문: [THREAT_MODEL.md](THREAT_MODEL.md)

---

## 1. 시스템 개요

WarmLogic은 AI 결정에 암호학적 증거를 첨부하는 이중 언어 런타임(Rust + Python)입니다. 시스템이 처리하는 항목:

- 양자내성 키 생성 및 서명 (ML-DSA-65)
- 비잔틴 장애 허용 합의
- 영지식 증명 생성 및 검증
- 추가 전용 원장 저장소
- P2P 네트워킹 (Kademlia DHT)
- 거버넌스 정책 집행

### 신뢰 경계

```
+---------------------------------------------------------------+
|  신뢰할 수 없음                                                 |
|  [네트워크]  [사용자 입력]  [외부 AI 모델]                       |
+---------------------------------------------------------------+
        |            |              |
        v            v              v
+---------------------------------------------------------------+
|  경계: Python 커널 (입력 검증, 정책 엔진)                       |
+---------------------------------------------------------------+
        |
        v
+---------------------------------------------------------------+
|  신뢰: Rust 코어 (암호화, 합의, 원장, ZK 증명)                  |
+---------------------------------------------------------------+
        |
        v
+---------------------------------------------------------------+
|  신뢰: 하드웨어 계층 (TPM/SEP — 현재 시뮬레이션)                |
+---------------------------------------------------------------+
```

**주요 신뢰 경계**: Python과 Rust 사이의 PyO3 FFI 인터페이스. 이 경계를 넘는 모든 데이터는 잠재적 적대적 데이터로 취급해야 합니다.

## 2. 위협 행위자

### A1: 외부 네트워크 공격자
- **능력**: 네트워크 트래픽 관찰 및 주입 가능
- **목표**: 합의 교란, 증거 위조, 노드 분할
- **관련성**: 높음 (Kademlia DHT는 UDP 기반)

### A2: 비잔틴 노드 운영자
- **능력**: BFT 클러스터에서 하나 이상의 노드 제어
- **목표**: 사기성 블록 커밋, 이중 투표, 합의 조작
- **관련성**: 높음 (BFT의 핵심 위협 모델)

### A3: DB 접근권이 있는 내부자
- **능력**: WarmLogic이 실행되는 머신에 물리적 접근
- **목표**: 원장 변조, 개인키 추출, 감사 로그 수정
- **관련성**: 높음 (금융 기관 시나리오)

### A4: 양자 적대자 (미래)
- **능력**: 암호학적으로 유의미한 양자 컴퓨터 접근
- **목표**: 과거 감사 기록의 서명 위조 ("지금 수확, 나중에 복호화")
- **관련성**: 중간 (10-15년 타임라인, 그러나 감사 기록은 장기 보존됨)

### A5: 악의적 AI 모델
- **능력**: WarmLogic SDK에 조작된 입력 제공
- **목표**: 정책 엔진 우회, 오해의 소지가 있는 증거 번들 생성
- **관련성**: 중간 (SDK 통합 패턴에 따라 다름)

## 3. 공격 표면 분석

### 3.1 암호화 모듈 (`warm_logic_rs/src/crypto.rs`)

**자산**: 개인키, 서명, 키 생성 엔트로피

| 위협 | 설명 | 현재 완화 | 격차 |
|------|------|----------|------|
| T-C1: 키 추출 | 메모리에서 개인키 유출 | `PQCKeypair`에 `Zeroize` + `ZeroizeOnDrop` derive | 키가 hex String으로 저장됨 — String의 `Zeroize`는 최선 노력이며 보장되지 않음 (힙 할당자가 복사본 유지 가능) |
| T-C2: 시뮬레이션 키 수용 | vHSM 시뮬레이션 키(`WARM-KEY-SIM-`)가 프로덕션에서 수용됨 | `verify_raw()`가 `WARM-KEY-SIM-` 접두사 거부 (82행) | 검증 경로에서만 확인됨. 서명 경로는 시뮬레이션 키를 거부하지 않음. 프로덕션 전용 모드 강제 런타임 플래그 없음 |
| T-C3: 키 생성 엔트로피 | 약한 RNG로 예측 가능한 키 생성 | OS 엔트로피를 사용하는 `fips204::ml_dsa_65::try_keygen()` 사용 | 추가 엔트로피 상태 확인 없음. FIPS 140-3 검증된 RNG 없음 |
| T-C4: 개인키 형식 | 개인키가 `pk_hex:sk_hex` 연결로 저장됨 | 기능적 | 비표준 형식. pk 부분이 수정되면 서명 경로가 잘못된 공개키 컨텍스트 사용 가능 |
| T-C5: 타이밍 부채널 | `verify_raw()`가 다양한 실패 조건에서 조기 반환 | 여러 조기 반환 (hex 디코드, 길이 확인 등) | 조기 반환이 키/서명 구조에 대한 정보 유출 가능. 애플리케이션 계층에서 상수 시간 아님 (기반 `fips204` 크레이트는 상수 시간일 수 있음) |
| T-C6: 서명 경로에서 패닉 | `py_generate()`가 `sign_raw().expect()` 호출 | `sign_raw()`가 `Result` 반환 | 114행의 Python 대면 `sign()`이 `.expect()` 사용 — 오류 반환 대신 실패 시 패닉. 이 모듈에 적용 시 `#![deny(clippy::expect_used)]` 위반 |

**우선순위**: T-C1 (키 제로화), T-C6 (패닉), T-C5 (타이밍)

### 3.2 합의 엔진 (`warm_logic_rs/src/consensus.rs`)

**자산**: 투표 무결성, 쿼럼 최종성, 블록 커밋

| 위협 | 설명 | 현재 완화 | 격차 |
|------|------|----------|------|
| T-B1: 위조된 투표 | 공격자가 무효한 서명으로 투표 제출 | `submit_vote()`가 모든 투표에 `MLDSA::verify_raw()` 호출 | 정상 작동 |
| T-B2: 이중 투표 | 같은 투표자가 같은 블록에 여러 투표 제출 | 블록당 투표자 ID용 `HashSet<String>` | 중복 voter_id 방지하지만 같은 검증자가 다른 키쌍 사용 감지 불가. 이중 투표 시도에 대한 슬래싱 없음 |
| T-B3: 투표 재생 | 이전 투표가 새 블록에 재생됨 | 블록 해시가 서명된 의도의 일부 (`VOTE:{block_hash}:{decision}`) | 투표에 term/epoch 번호 없음. 재사용된 블록 해시에 대한 투표가 이론적으로 재생 가능 |
| T-B4: 쿼럼 조작 | 공격자가 쿼럼 도달에 충분한 노드 제어 | 표준 BFT 임계값: `(2N/3)+1` | 검증자 세트 관리 없음. 동적 검증자 추가/제거 메커니즘 없음. 스테이크 기반 검증자 선택 없음 |
| T-B5: 메모리 고갈 | 공격자가 많은 블록 해시에 투표 플러딩 | `votes` HashMap 크기 제한 없음 | 무제한 HashMap 성장. 오래된/미커밋 투표 세트 제거 없음 |
| T-B6: 뷰 변경 없음 | 리더 실패로 합의 차단 | 뷰 변경 프로토콜 없음 | 단일 리더 가정. 리더 교체 또는 타임아웃 메커니즘 없음 |

**우선순위**: T-B5 (DoS), T-B3 (재생), T-B6 (활성화)

### 3.3 영지식 증명 (`warm_logic_rs/src/proof_zk.rs`)

**자산**: 증명 무결성, 커밋먼트 바인딩, 증인 비밀성

| 위협 | 설명 | 현재 완화 | 격차 |
|------|------|----------|------|
| T-Z1: H 생성기 조작 | 알려진 k에 대해 H = k*G이면 Pedersen 커밋먼트가 은닉적이지 않음 | `from_uniform_bytes`를 통해 `SHA3-512("WarmLogic_H_Generator")`에서 H 파생 | 정확함: nothing-up-my-sleeve 도출. 알려진 문제 없음 |
| T-Z2: 증명에서 약한 난수 | Sigma 프로토콜에서 예측 가능한 k,s | `Scalar::random(&mut OsRng)` 사용 | OS 엔트로피에 의존. 추가 난수 검사 없음 |
| T-Z3: 가변 시간 연산 | 가변 시간 스칼라 곱셈의 부채널 유출 | 검증에서 `vartime_multiscalar_mul` 사용 | 검증은 허용됨 (공개 입력). 증명 생성도 안전 (랜덤 k,s). 설계 선택으로 문서화됨 |
| T-Z4: 증명 변조 가능성 | 제3자가 같은 커밋먼트에 대해 대안적 유효 증명 생성 | Merlin 트랜스크립트를 통한 Fiat-Shamir | 트랜스크립트가 챌린지를 커밋먼트 + 발표에 바인딩. 표준 구성 |
| T-Z5: 커밋먼트 재사용 | 여러 증명에서 같은 커밋먼트 사용 시 정보 유출 | 커밋먼트 중복 검사 없음 | 애플리케이션 계층에서 사용된 커밋먼트 추적 필요 |

**우선순위**: T-Z5 (커밋먼트 재사용 추적)

### 3.4 원장 (`warm_logic_rs/src/ledger.rs`)

**자산**: 블록 무결성, 상태 일관성, 추가 전용 속성

| 위협 | 설명 | 현재 완화 | 격차 |
|------|------|----------|------|
| T-L1: 원장 변조 | Sled 데이터베이스 파일의 직접 수정 | 해시 체인 (각 블록이 이전 블록 해시 참조) | Sled는 임베디드 DB — 파일시스템 접근 권한이 있는 누구나 수정 가능. 디스크 암호화 없음. 해시 체인 외 시작 시 무결성 검사 없음 |
| T-L2: Sled 데이터 손상 | Sled 베타 품질 스토리지 엔진이 데이터 손실 | Sled 내장 크래시 복구 | Sled는 pre-1.0 (v0.34.7). 크래시 시 데이터 손실 알려진 문제. 외부 백업 없이 금융 등급 스토리지에 부적합 |
| T-L3: 상태 루트 조작 | 잘못된 상태 루트로 무효한 잔액 증명 허용 | 트랜잭션 재생에서 상태 루트 재계산 | 효율적인 포함/배제 증명을 위한 Merkle 트리 없음 |

**우선순위**: T-L1 (파일시스템 접근), T-L2 (Sled 신뢰성)

### 3.5 PyO3 FFI 경계 (`warm_logic_rs/src/lib.rs`)

**자산**: 언어 경계 간 데이터 무결성, 메모리 안전성

| 위협 | 설명 | 현재 완화 | 격차 |
|------|------|----------|------|
| T-F1: 과대 입력 | Python이 매우 큰 문자열/바이트를 Rust에 전달 | FFI 경계에서 입력 크기 검증 없음 | Python 입력 기반으로 Rust가 무제한 메모리 할당 가능 |
| T-F2: 유효하지 않은 UTF-8 | Python이 non-UTF-8 바이트를 문자열 인수로 전달 | PyO3가 UTF-8 검증 처리 | 낮은 위험 — PyO3가 str 타입 강제 |
| T-F3: 동시 접근 | 여러 Python 스레드가 Rust를 동시 호출 | 긴 작업에 대한 GIL 해제 | Rust 구조체가 본질적으로 스레드 안전하지 않음. BFTEngine이 `&mut self` 사용하여 동시 접근 방지 |

**우선순위**: T-F1 (입력 크기 검증)

### 3.6 네트워크 계층 (Python Kademlia DHT)

**자산**: 노드 신원, 라우팅 테이블 무결성, 메시지 진정성

| 위협 | 설명 | 현재 완화 | 격차 |
|------|------|----------|------|
| T-N1: 이클립스 공격 | 공격자가 악의적 노드로 라우팅 테이블 채움 | 메시지에 PQC 서명 검증 | 단일 버킷 Kademlia — k-버킷 분할 없음. 현재 구현에서 쉽게 이클립스 가능 |
| T-N2: 시빌 공격 | 공격자가 많은 신원을 저렴하게 생성 | 작업 증명 또는 스테이크 요구 없음 | 키 생성에서 노드 ID 파생 — 무제한 신원 생성 가능 |
| T-N3: 메시지 스푸핑 | 합법적 노드에 귀속된 위조 메시지 | ML-DSA-65로 메시지 서명 | 서명 검증이 스푸핑 방지 |
| T-N4: UDP 증폭 | 공격자가 WarmLogic 노드를 증폭기로 사용 | 속도 제한 없음 | 표준 UDP 증폭 위험 |
| T-N5: 블록 전파 | StitchServer 미완성 — 블록이 전파되지 않음 | 해당 없음 | **치명적 격차**: BFT 합의는 존재하지만 블록이 노드 간 전파 불가. 시스템은 사실상 단일 노드 |

**우선순위**: T-N5 (치명적 기능 격차), T-N1 (이클립스), T-N2 (시빌)

### 3.7 거버넌스 커널 (Python)

**자산**: 정책 집행, 중지 기능, 운영 모드 무결성

| 위협 | 설명 | 현재 완화 | 격차 |
|------|------|----------|------|
| T-G1: 정책 우회 | 정책 평가를 피하도록 조작된 악의적 입력 | 정책 엔진이 모든 행동 검증 | 정책 엔진 규칙이 구성 가능 — 잘못된 구성이 격차 생성 가능 |
| T-G2: 중지 회피 | 시스템이 중지해야 하지만 하지 않음 | e_stab 공식과 함께 4-모드 시스템 (NORMAL → VETO_LOCK) | Python 기반 — 손상된 Python 프로세스가 중지 검사 건너뛰기 가능 |
| T-G3: 감사 로그 변조 | 추가 전용 JSONL 로그 수정 | 항목당 SHA-256 무결성 해시 | 외부 증인 없음. 같은 파일시스템에 저장된 로그 — 루트 접근으로 삭제 또는 잘라내기 가능 |

**우선순위**: T-G2 (Python vs Rust에서 중지 집행), T-G3 (감사 로그 무결성)

## 5. 보안 감사 권고사항

### 감사 범위 (권장)

**1단계 — 암호화 코어** (최우선)
- `warm_logic_rs/src/crypto.rs` — ML-DSA-65 키 관리, 서명/검증
- `warm_logic_rs/src/proof_zk.rs` — Sigma 프로토콜, Pedersen 커밋먼트
- `warm_logic_rs/src/consensus.rs` — BFT 투표 검증
- 초점: 정확성, 부채널, 메모리 안전성

**2단계 — 스토리지 및 상태**
- `warm_logic_rs/src/ledger.rs` — 블록 체인 무결성, 상태 관리
- Sled 데이터베이스 신뢰성 평가
- 해시 체인 검증 완전성

**3단계 — FFI 및 통합**
- `warm_logic_rs/src/lib.rs` — PyO3 경계 안전성
- Python 커널 정책 집행
- 입력 검증 완전성

### 감사 전 조치

1. 모든 공개 Rust API에 `cargo-fuzz` 타겟 추가
2. `cargo-audit` 실행 및 모든 권고사항 해결
3. FFI 경계에 입력 크기 제한 추가
4. Python 대면 서명 경로의 `.expect()` 수정
5. 코드 주석에 모든 알려진 제한 사항 문서화

## 6. 알려진 제한 사항 (취약점 아님)

research prototype에서 문서화된 설계 제한 사항:

| 제한 | 영향 | 계획 |
|------|------|------|
| vHSM 시뮬레이션됨 | 하드웨어 신뢰 앵커 없음 | TPM/SEP 통합 계획됨 |
| 단일 버킷 Kademlia | 대규모 네트워크에 확장 불가 | K-버킷 분할 로드맵에 있음 |
| StitchServer 미완성 | 사실상 단일 노드 | P2P 블록 전파 개발 중 |
| UC 증명 없음 | 합성성 공식 증명되지 않음 | 학술 협력 계획됨 |
| Sled 베타 | 스토리지 신뢰성 우려 | RocksDB/SQLite 마이그레이션 평가 |
| macOS 전용 하드웨어 증명 | 제한된 크로스 플랫폼 지원 | Linux TPM 지원 계획됨 |
| ~60% 테스트 커버리지 | 암호화 코드에 불충분 | 퍼징으로 80%+ 목표 |
